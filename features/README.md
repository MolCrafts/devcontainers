# MolCrafts features

Features are split by **toolchain**; repository names survive as meta-features that only compose them. See the [root README](../README.md) for the option tables and the reasoning behind each design choice.

| id | kind | provides |
|---|---|---|
| `python` | toolchain | uv, uv-managed CPython, ruff, ty, prek |
| `rust` | toolchain | rustfmt, clippy, rust-src, wasm32, wasm-pack, maturin |
| `node` | toolchain | corepack, biome |
| `native` | toolchain | CMake ≥ 4, Ninja, clang tooling, ccache, Doxygen |
| `torch` | toolchain | uv `torch-backend` resolution, torch CMake prefix |
| `molpy` | meta | `python` |
| `molrs` | meta | `rust` + `native` + `python` |
| `molvis` | meta | `node@22` + `node` + `python` |
| `molexp` | meta | `node@22` + `node` + `python` |
| `molnex` | meta | `python` + `native` + `torch` |

## Layout

The directory name **is** the feature id — the publisher derives the OCI tag from it, so this tree has to stay flat. CI asserts `id == basename(dir)`.

```
src/<id>/devcontainer-feature.json    metadata, options, dependsOn/installsAfter
src/<id>/install.sh                   runs as root at build time
src/<id>/README.md                    GENERATED at publish time — do not hand-write
test/<id>/scenarios.json              named scenarios
test/<id>/<scenario-name>.sh          one script per scenario key
```

## Adding a feature

1. `src/<id>/devcontainer-feature.json` — start `version` at `1.0.0`. Never republish an existing version; the publisher will reject it.
2. `src/<id>/install.sh` — needs `#!/usr/bin/env bash`, `set -Eeuo pipefail`, and the executable bit. CI gates all three plus shellcheck, because a missing shebang once made a failing install report success.
3. `test/<id>/scenarios.json` plus a script per scenario. CI fails a feature with no scenarios rather than silently covering nothing.
4. Options arrive as upper-cased env vars with punctuation stripped: `pythonVersion` → `$PYTHONVERSION`.

## dependsOn vs installsAfter

`dependsOn` **installs** the dependency; `installsAfter` only **orders** an already-requested one.

Features are deduplicated by id *and options*, so a `dependsOn` edge carrying different options than the user's own declaration installs the dependency twice. That is why only `rust` uses `dependsOn` for an external feature — the whole ecosystem is on stable, so there is no version to diverge on. `node` uses `installsAfter` and fails loudly if Node is missing, because repos pin different majors.

Meta-features are the exception: they are pure `dependsOn` with fixed options, which is exactly what it is for. A repo that needs different options skips the meta and declares the toolchain features directly.

## Testing

```bash
devcontainer features test ./features -f python --skip-autogenerated
```

Meta-features resolve their graph from ghcr, so they only pass against published versions — `release.yml` tests them right after publishing.
